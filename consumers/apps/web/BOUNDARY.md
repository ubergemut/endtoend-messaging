# EndToEnd presentation boundary

This complete React frontend preserves the existing EndToEnd product, guide, appearance, contacts, threads, groups, attachments, unread navigation, expiry, notices and server-view displays. Its source remains declared **AGPL-3.0-only**. Moving a historical file or changing its imports does not establish independent provenance or grant proprietary rights; the release assessment must examine its concrete history.

The current build imports only the independently compiled MIT `@e2ee/client/standalone` and `@e2ee/protocol/standalone` packages and its declared React/Vite dependencies. Build the SDK first (`yarn build:sdk`), then run `yarn workspace @e2ee/web run check`, `yarn workspace @e2ee/web test` and `yarn workspace @e2ee/web build`. No agent, session, crypto, WASM or contract implementation is imported or bundled. The old unused `sealFile`/`openFile` AES helpers were removed; the unchanged 25 MiB selection limit remains. All file encryption/decryption executes in the agent.

`/agent-config.json` supplies bare secure `agentUrl` and `relayUrl` origins. The product and trusted agent require different origins. The product opens the trusted window synchronously, authenticates its ready message by both window and origin, transfers one MessagePort, and matches the connection nonce. Device-secret entry, device-key generation, storage, identity approval and verification stay in that trusted window. The product holds presentation data and messaging authorization tokens, never the device secret, private keys or vault.

Default configuration preserves native relay handle/password registration/login. Optional flat `audience` and `grantPath` fields switch to an existing host login (`nativeAuth: false` can make this requirement explicit). The legacy nested `host: { audience, grantPath }` form is also accepted, but combining flat and nested forms is refused. The host authenticates its own session externally; the product POSTs only to a strict same-origin `grantPath` with the host cookie and receives the public `MessagingGrant`. `RelayService` checks metadata, audience, expiry, bootstrap path and token/account identity. Relay requests omit cookies and carry only the explicit messaging token; host passwords/cookies/assertion-signing keys are never forwarded. Logout clears presentation immediately and requests token revocation. Host grants remain in memory and are reacquired after page reload; the existing native Stay behavior is preserved.

Every view refresh and operation checks the current session generation and unlocked status before publishing results. Locking, revocation, connection failure, account switch, page lifecycle and logout clear cached messages, requests, friends, groups, pending drafts, notifications and attachment object URLs. Delayed responses cannot reintroduce data. The SDK's local `revoke()` terminates the local capability only; it is not a server event feed or a substitute for relay token revocation. Explicit status/sync and the relay's existing WebSocket notifications drive refreshes.
