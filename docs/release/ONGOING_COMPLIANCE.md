# Retained source, corrections and later releases

Responsible role: **Project owner** (the maintainer operating this release; no external reviewer is appointed). Public contact: [repository Issues](https://github.com/ubergemut/endtoend-messaging/issues). An operator of another deployment must identify its own responsible maintainer/contact and preserve the same user source opportunity.

This process applies to the assessed messaging/full frontend/desk 0.2.0 and SDK 0.2.1 and their successors. It implements the [delivery/retention policy](../../messaging/docs/release/STEP_8_DISTRIBUTION_POLICY.md), [source/license assessment](STEP_9_SOURCE_AND_LICENSE_ASSESSMENT.md) and [source routing/terms guide](../deployment/SOURCE_DELIVERY.md). It does not change frozen artifacts, upstream grants or earlier recipients' rights.

## Source delivery and retention

Use direct network delivery under the recorded AGPL section 6(d)/section 13 route, with full source/license/notices beside exact binaries/browser downloads and prominent service source access. This project does not substitute a section 6(b) physical-product written offer or a request queue for those downloads. Keep required source free of account, payment, NDA or extra covered-right restrictions. Publish and verify matching source before external beta/browser/service delivery.

Retain immutable source/runtime/SDK archives, manifests, catalogs, licenses/notices, modification records, assessment/owner decisions and verification evidence indefinitely as project policy, with an independent backup. Keep exact source online while its version is running, downloadable, mirrored under project control or supported for browser caching, rollback or recovery. Do not redirect an old version's source URL to a newer archive. Record any exceptional retirement and its compliant replacement before changing endpoints; there is no automatic deletion date.

Maintain a retained-version register identifying catalog/artifact/manifest hashes, deployment/download locations, first/last availability, cache/rollback support, source endpoints, verification dates and the responsible operator. A service rollback changes the running-version mapping and preserves the newer version's source. A mirror or upstream repository does not take over the project's responsibility for its own offer. Check retained links before releases and after hosting/domain/CDN/proxy changes.

## A source request or reported problem

The project owner receives Issues reports and may delegate investigation to a named maintainer. Ask only for the component/version, observed page or executable, source URL and expected/observed hash when available. A recipient need not disclose messages, a vault, device secrets, account credentials or private business source to obtain required source. If the reporter cannot identify a version, help them use `/release.json`, the visible source entry or CLI/MCP metadata.

1. Confirm the affected version against the retained register and exact catalog. Preserve the report, failing response/hash and relevant release record. A working newest-version link does not resolve an older-version failure.
2. Restore the correct immutable source, manifest or notice from verified backup/mirror and check anonymous GET/HEAD, visible UI/adapter discovery and every applicable hash through the real delivery path. Source remains directly downloadable while the issue is handled; the issue thread is not an approval gate.
3. If a required source item was missing, provide the complete corrected source/notices with clear version correspondence. Keep original evidence and mark its defect/superseding record rather than overwriting history or falsely claiming an unchanged hash. Assess whether source, runtime, catalog or owner decision identities must change.
4. Until matching source/notices are available, stop affected new downloads/browser delivery or service exposure that would continue the defective offer. Preserve user state and previous valid source. Resolve the actual source/license problem rather than merely closing the report.
5. Record the cause, correction, verification and affected retained versions; update public release notes/issue with the usable source destination. Re-run relevant completeness/delivery regressions so the same omission cannot silently recur.

The project sets no source-request fee, NDA, discretionary approval process or arbitrary waiting period. Correct a confirmed failure promptly; do not claim a guaranteed response time or source availability that the operator has not arranged.

## Later-version assessment

For each changed candidate, inventory actual source/build/runtime/bundle inputs and compare them with the last assessed graph. Regenerate exact manifests/catalogs and required notices/source closure. Run affected behavior, source completeness and clean-user delivery checks. Record commands/results and supported platform/recovery limits. Ordinary application fixes within the assessed architecture need relevant checks and a short change record, rather than a new outside opinion.

A named human maintainer must review the changed scope when it includes:

- A dependency/version/license or source-origin change, a new asset, or a different permissive/secondary-license choice.
- A generator, preferred source, embedded helper/runtime, build chain or material bundle-content change.
- New copied UI, frontend provenance, private host imports, executable callbacks, shared implementation/state structures or other changed program coupling.
- New source exclusions, distribution routes, service/product terms, hardware/preinstallation/signing restrictions or a different installation-information conclusion.

Write the actual evidence, reasoning, grants, remaining issues and reviewer/date. Preserve recipient choices and original notices; do not use mechanical pass flags as legal reasoning. Resolve material uncertainty with more complete source, refactoring, a compatible replacement or targeted advice. Professional advice can reduce risk but no outside certificate is a routine release gate. No external person is contacted or paid without authorization.

Bind the favorable internal assessment and owner content decision to the exact new hashes. Actual publication/deployment requires its distinct authorization and verification of live external downloads/source/notices. Preserve prior decisions and failed/superseded artifacts. Use the project owner’s retained internal release checklist, public release verification tools, contribution provenance rules in [CONTRIBUTING.md](../../CONTRIBUTING.md) and [per-project guide](../deployment/PROJECT_INTEGRATION.md); neither MIT SDK use nor a cosmetic frontend change grants an exception to covered AGPL implementation.
