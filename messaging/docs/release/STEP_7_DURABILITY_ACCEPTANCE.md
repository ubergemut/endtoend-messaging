# Synthetic durability, upgrade and recovery acceptance

`scripts/test-messaging-durability.mjs` exercises the public managed launcher, real persistent PGlite relay and independent executable device agents. All accounts, vaults, media, database files and checkpoints are newly generated below an explicitly checked OS temporary directory. It does not read `.env`, the checkout's `.pglite`, personal browser storage or an existing account/vault. Every listener binds `127.0.0.1:0` once; there are no port availability probes.

Run the harness with Node's TypeScript loader installed from the offered locked source workspace:

```powershell
node --import tsx scripts/test-messaging-durability.mjs --source-root "C:\FreshPublicSource" --runtime-root "C:\FreshPublicRuntime" --rollback-root "C:\PreservedStep4Runtime" --receipt "C:\Evidence\durability.json"
```

`--source-root` and `--runtime-root` default to this script's parent workspace. The latter selects the built public launcher/device-agent implementation and browser application distributions; omit it when testing the built source workspace itself. `--rollback-root` is optional and selects a preserved older runtime for an incompatible application rollback refusal. Its code is executed against newly created synthetic current state only; that historical installation is never modified. The receipt records the selected roots, Node version, exact implementation/WASM hashes, named assertions, checkpoint/file/wire hashes and limitations. Temporary synthetic state is closed, removed and checked absent before a successful receipt is returned. A failed assertion does not produce a passing receipt.

The assertions include:

- A deliberately constructed schema-1 PGlite database migrates through the actual current managed launcher to schema 2, preserving accounts, sessions, group epochs, encrypted queue/media rows and acknowledgement tombstones. A future-version ledger is refused. This fixture is created as version 1; the harness never lowers a current database's ledger.
- A real media upload succeeds at the relay and its HTTP response is discarded. The sealed committed file intent survives independent agent and relay process restarts. Retrying uses the exact media ID and encrypted upload body, and the recipient obtains byte-identical file contents with the original reply/timer.
- A real envelope send and its acknowledgement succeed at the relay and their HTTP responses are discarded. The stopped sealed sender vault contains its committed outbox/user intent, while the recipient vault contains the committed message/ratchet and pending ACK. Restarting a compatible application retains those stores, resends the exact envelope/tag, preserves the cryptographic state and message count, and flushes the saved ACK. Replaying the acknowledged envelope returns its original ID without requeueing it; reusing its tag for different content refuses.
- When supplied, the actual historical schema-1 runtime refuses the current schema-2 state without opening a device vault. A separate compatible rollback rehearsal selects a copied prior presentation build with the current compatible backend/agents. This does not claim compatibility with an unavailable historical backend.
- A matching complete closed managed-root and all-device checkpoint includes encrypted blobs and committed pending send/ACK state. Hash-verified recovery uses new isolated locations, while the original remains stopped. Identities, verified safety numbers, messages/files, pending intents and cryptographic ratchets survive; direct/group messaging then continues. No participant advances between checkpoint and recovery.
- Group membership changes rotate the sender key/epoch and archive old pending ciphertext rather than delivering it into the new membership. Remaining members receive new traffic, the removed participant does not, and a stale-epoch relay submission refuses.
- Wrong device secrets, a second vault writer, cross-account vault reuse, unapproved device replacement and changed peer identities refuse. Explicit replacement retires the old identity; the old vault's bytes remain preserved. A managed root marked `recoveryRequired` refuses before creating/opening relay storage.

Test-only inspection decrypts only this run's synthetic sealed records in memory using its generated device secret. Public operations continue to run through the published agent/headless interface; no testing API is added to production. Crypto state comparisons canonicalize the order of Rust map entries and compare hashes of the exact serialized key/ratchet bytes. The proxy temporarily holds incoming delivery receipts during those comparisons because a legitimately received receipt advances the receiving ratchet; it releases them afterward. A relay fault proxy records synthetic request bodies in memory to check stable retries and never includes secret material or full ciphertext bodies in the receipt. Coordinated shutdown sends the public agent `close` command before closing its child transport, ensuring the vault is flushed and its writer lease released on Windows too.

The current receipt, command and release artifact hashes belong in the step-7 completion record. Earlier standalone acceptance counts remain historical evidence and are not imported as a current pass by this harness.

## Recovery limits and explicit new-device enrollment

There is no independent monotonic anchor for an arbitrary external replacement of a vault file. Neither a vault's internal revision nor a matching old relay backup proves that no peer advanced. The harness does not claim that manually copying an old same-identity vault onto a current filesystem is detectable or supported. The supported fail-closed marker is an operator quarantine guard, not an automatic stale-backup detector. The bounded matched-checkpoint rehearsal does not establish general history recovery, PostgreSQL deployment recovery or browser-origin/storage migration. See [storage and recovery](../deployment/STORAGE_AND_RECOVERY.md).

If current cryptographic state cannot be recovered and a new identity is deliberately chosen, stop every old agent and preserve the old vault, blobs and failed/current relay evidence offline. Create a new empty vault location with a new device secret and use the documented headless `unlock({handle,password,replaceKeys:true})` operation explicitly for that account. First trying a new vault without `replaceKeys` must refuse an already enrolled account. Replacement changes the account's public device identity and invalidates the prior device; peers must review the changed identity before trusting it. It does not restore history or committed pending work from the old vault, and copying old ratchets into the new device is unsupported. The acceptance run demonstrates this mechanism only on its disposable third synthetic account after the matched recovery test has completed.
